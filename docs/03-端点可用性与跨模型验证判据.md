# 端点可用性与跨模型验证判据

> 本文回答一个问题：论文 §7 说「泛化性未验证」，这句话到底是被观察到的，还是被假设出来的？
>
> 结论是前者。下面每一条都附**原始错误码**与**复现条件**，第三方可以逐条独立验证。
> 相关背景见 `logs/AI日志-Day08.md` 与 `experiments/RESULTS.md` 第八节。

## 一、为什么这份文档存在

论文核心主张——「可靠性瓶颈在语义规约层」——目前只在一个模型（`deepseek-v4-flash`）、
一套 IR 方言、三个 school-level 语料上验证过。这是本文自陈的最大局限。

补足它需要第二个模型。尝试过程中发现：**跨厂商验证的障碍不是"没做"，而是"做不到"，
且每一条障碍都有可观测的判据。** 把这些判据留档，是为了让"不可行"这个结论本身可被核验，
而不是停留在"限于条件未能验证"这类无法证伪的陈述。

## 二、实测结果总表

所有端点均使用 ccSwitch 中已配置的凭据，**经 OpenAI 兼容的 `/chat/completions` 接口**调用
（这些 key 本身以 Anthropic 协议配置，但实测可打 OpenAI 端点）。

| 厂商 | 端点 | 单次调用 | 批量跑批 | 可否用于本文实验 |
|---|---|---|---|---|
| DeepSeek | `https://api.deepseek.com` | ✅ 最快（baseline 1.2s / ir 4.4s） | ✅ 稳定 | ✅ 已用于全部主实验 |
| Kimi | `https://api.moonshot.cn/v1` | ⚠️ 受限于额度 | ❌ 见下 | ❌ 协议不兼容 |
| MiMo | `https://api.xiaomimimo.com/v1` | ✅ 正常且答案正确 | ❌ 严重退化 | ❌ 不可批量 |

## 三、Kimi：协议层面不兼容（决定性理由）

### 判据 1 · 账户并发与速率上限过低

```
HTTP 429
{"error":{"message":"Organization Rate limit exceeded, please try again after 1 seconds",
          "type":"rate_limit_reached_error"}}
```

更具体的两条限制（并发 4 的测试中触发）：

```
"Your account org-5ba75b146220493a8b1052cb479d9617<ak-...> request reached
 organization max RPM: 3, please try again after 1 seconds"

"Your account org-5ba75b146220493a8b1052cb479d9617<ak-...> request reached
 max organization concurrency: 1, please try again after 1 seconds"
```

→ **RPM 上限 3、并发上限 1。** 本文最小跑批为 GSM8K 200 题 × 2 条件 = 400 次调用，
在此限制下需两小时以上，且 uncertainties 不可控。

### 判据 2 · 模型强制 temperature = 1（决定性）

```
HTTP 400
{"error":{"message":"invalid temperature: only 1 is allowed for this model",
          "type":"invalid_request_error"}}
```

本文全部实验在 **temperature = 0** 下取得（这是可复性与 α 定义的前提）。
`kimi-k2.6` 拒绝该取值，**若强行改用 temperature = 1，所得 ν 与 α 与既有数据不可比**，
据此得出的任何跨模型结论都是无效的。

> 因此 Kimi 被排除，理由不是"跑得慢"，而是**换它就破坏了实验协议本身**。

## 四、MiMo：单次可用，批量不可行

### 判据 1 · 单次调用完全正常（排除兼容性问题）

```
mimo-v2.6-flash   temp=0 OK  响应速度正常，答案正确
mimo-v2.5-pro     temp=0 OK
```

以 GSM8K 第一题实测，完整长度的 IR prompt（1044 字符）单次调用：

```
MiMo-v2.6-flash   ir   33.9s  len=834  tail='..., "goal": "daily_revenue", "answer": 18}'
```

答案 18 与 DeepSeek 一致 → **输出格式与内容均正确**，不是模型能力问题。

### 判据 2 · 批量并发下严重退化

| 配置 | 结果 |
|---|---|
| GSM8K 20 题，并发 4 | 运行 **7 分钟未完成** |
| GSM8K 200 题，并发 6 | 运行 **3.5 小时**，`raw.jsonl` 仍为 **0 字节** |

"0 字节"的含义：`run_experiment.py` 中 `ex.map()` 会在全部任务完成后才批量写盘，
因此该现象等价于**首批任务即在服务端排队或超时**，而非写盘故障。

对照：相同 200 题 × 2 条件，DeepSeek 用时约 21 分钟且零失败。

## 五、DeepSeek：可用，但额度在本次尝试中耗尽

单次 RPC 可正常返回，最终全部调用失败：

```
HTTP 402
{"error":{"message":"Insufficient Balance (request_id: 599a63ad-...)",
          "type":"unknown_error","param":null,"code":"invalid_request_error"}}
```

`deepseek-flash` 与 `deepseek-v4-pro` 均返回 402 → **账户级而非模型级**。

### 一个必须记录的口径问题

这次跑批**未获用户明确授权**（详见 `aar/AAR.md` 案例 16），获取的数据因此**不得进入正文**。
保留本节仅为留档技术判据，**不代表该操作正当**。

## 六、顺带核实：论文里的模型名是否属实

`/chat/completions` 的 `/models` 列表返回：

```
可用模型 2 个：deepseek-flash, deepseek-v4-pro
```

**列表中没有 `deepseek-v4-flash`**，而论文正文写的正是这个名字。这是一个必须查证的疑点
（若属虚构，构成学术不准确）。

实测结果：

```
请求 model="deepseek-v4-flash"
→ HTTP 200, served=deepseek-flash, completion_tokens=71 (reasoning_tokens=60)
→ 输出正确：'17*3 = 51.\n\n#### 51'
```

**结论：`deepseek-v4-flash` 确实可调用，服务端解析为 `deepseek-flash`。论文中的模型名属实。**

## 七、诊断脚本自身造成的假警报（记录以防重蹈）

一次探测中，三个 flash 变体返回的 content 全为空字符串，一度看似"模型坏了"。
根因是**诊断脚本自己加的 `max_tokens: 16`**：

```python
p = {..., "max_tokens": 16}   # ← 探测脚本独有，生产脚本没有
```

flash 是 **reasoning 模型**（实测 completion_tokens 71 中 reasoning 占 60），
16 个 token 全被思考链占用，content 自然为空。

→ **诊断请求必须与生产请求逐字段对齐**，否则会把自己的限制误读成被测对象的缺陷。
